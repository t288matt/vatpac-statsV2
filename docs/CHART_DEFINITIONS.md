# Chart definitions

*Describes main (the commit production runs is shown by `bash ops/deploy.sh --status`); behaviour added by later changes that are not yet deployed is listed in CHANGELOG.md.*


Every in-scope v1 chart and what replaced it, for the Grafana dashboards in `grafana/dashboards/`. Dates are DD-MM-YYYY and all times UTC.

Status key: **KEPT** same question and definition (SQL rewritten against the v3 views); **CHANGED** same question, definition altered (see the difference column); **UNVERIFIED** the definition is the analytics agent's best reading and awaits the owner's Metabase export; **DROPPED** not rebuilt (reason given).

Look (issue 280, 06-11-2026): every dashboard page (Traffic, Routes, Aircraft, Pilots records, the six ATC pages including Promotions, Monday events, Monthly, Collector health, and, in batch 4, Pilot origins, Military and Pilot onboarding) has the same look as the former Live now page (in-cell bars, single-colour ranked bars with values, legend tables, donuts with a legend table, plain stat card, the hours-online charts as bar charts). No panel's query, format, window or column names changed (proved by `tests/test_dashboards_sql_unchanged.py`), so every definition below still stands. The conventions are in [RUNBOOKS/dashboards.md](RUNBOOKS/dashboards.md).

Panels read views and lookups only: `flight`, `controller_session_merged`, `online_now` and `data_freshness` from migration `20261007000004_views.sql`, most of the rest from migration `20261007000010_analytics_views.sql`, `controller_summaries` from migrations `20261008000030` and `20261008000031`, and `pilot_sample` from migration `20261008000080` (the `flight` view is a thin view over the finished-flights table `flight_summary`, filled once per finished flight by `write_finished_flights()`; migration `20261013000200` made it so, live since 13-10-2026; `flight_ext`, `movements`, `cohorts` and `monday_attendance` follow it). Since phase 5 (migration `20261013000300`, live since 13-10-2026 10:05:56 UTC) `flight_summary` is the only flight store: the old per-piece table and the old merging view are gone, and no panel reads either. Everything below describes the charts as they are. There is no backfill, so every chart starts empty at go-live.

Verification: `python grafana/validate_dashboards.py` parses every panel query with sqlglot and resolves the views it reads, and `ops/check_panels.py` runs every panel query through a live Grafana's own API (expect 0 errors; a panel with no rows is fine while data is young). Integration tests run the queries on synthetic rows. "Runs without error" is not the same as "answers the question correctly": the Test column names the automated tests that assert each panel, every name there is a test function that exists, and every panel also runs as the read-only role in `test_every_panel_query_runs_as_grafana_ro`. Entries marked "Live-data check (manual)" are checks for a person to make once enough real data exists; no test performs them. A test does not prove the definition is what the owner wants, only that the panel does what its row says.

### Why these charts were dropped, and what else was simplified

**Frequency matching and sector matching are not part of v3** (SPEC sections 1, 10 and 13). The collector stores pilots inside the Australian boundary polygon and whitelisted controllers, with their sessions and positions. It does not work out which pilot was talking to which controller, nor which sector an aircraft was in. Every v1 chart that depended on either was dropped rather than approximated, because an approximation would show numbers that look authoritative and are not.

- **Frequency matching** (cards 41, 43, 98, 133, 148): also removed as a consequence are the ATC-contact percentage column of the popular VFR routes chart (card 59) and the "aircraft handled" part of the top service providers score (card 108, now hours online only). Controller frequencies are still stored (integer Hz) and the online-controllers list shows them in MHz; they are just not matched to pilots.
- **Sector matching** (cards 51, 88, 102, 104 to 107): needs sector boundaries, occupancy tracking and transition detection. If sectors are wanted later they belong in a separate project that reads `pilot_position`; raw positions are kept for 90 days, but the charts would start from the day the work is done.
- **Milk Run Monday fastest and slowest** (cards 62, 86, 132): dropped by decision (SPEC section 10). The controllers-per-month chart (card 131) and the local-pilot share (card 134) remain on the Monday event dashboard.
- **v1 pipeline monitors** (cards 121 to 126, 139): these watched v1's enrichment and matching jobs, which do not exist in v3. The Monitoring dashboard (`grafana/dashboards/monitoring/collector-health.json`) replaces them: snapshot age, last successful poll, missed snapshots, errors, rejected values and unknown-callsign controllers. The v1 freshness gauges (cards 118 and 120) live on as the snapshot-age and controller-sighting-age panels.

Simplifications that are not drops:

- Pilot "online" and "active" counts come from `network_snapshot` and the `flight` view, not from enrichment tables.
- Military aircraft are a boolean in the `aircraft_type` lookup instead of a long hard-coded list in each query (card 65). Cards 66 and 78 identify RAAFv flights by the flight-plan remarks, as v1 now does.
- Airline, aircraft category and pilot home region are lookups (`airline`, `aircraft_type`, `region_map`), seeded by migration `20261007000011_seed_analytics_lookups.sql`. Unlisted codes show as Other or Unknown instead of being silently dropped.
- Home-region tests use the `home_icao_prefixes` setting (default `Y`) rather than a hard-coded `Y`.
- v1 history (ADR-035, loaded into production on 05-11-2026) gives the charts data from 24-08-2025 (flights to 06-03-2026, controller sessions to 15-03-2026), with no data after those dates until go-live (07-10-2026); see [RUNBOOKS/import-v1-history.md](RUNBOOKS/import-v1-history.md) for what the charts show. Live data starts at go-live. Since 08-11-2026 (issue #307) the dashboards no longer carry a data-history banner (only "All times are UTC. Figures cover VATPAC airspace."; the promotions page reads the whole network and carries only "All times are UTC."), so the gap between the two import end dates and go-live is not stated on the pages; panels spanning it show a visible gap. The 30 to 90 day measures of the controller retention dashboard stay empty or misleading until history accumulates.

## Flights in progress (ADR-025, superseded by ADR-030)

Nothing is shown in progress. Since issue 89 phase 3 (migration `20261013000200`, live since 13-10-2026 08:14:12 UTC) a flight is written to `flight_summary` only after the flight itself has had no position for 8 hours of stored data (`flight_quiet_hours`, measured against the newest stored snapshot; per flight since migration `20261012000200`), so every flight count, rank and airborne-time sum contains finished flights only, about 8 hours after the flight's last position (an earlier leg does not wait for a later one). No panel carries an in-progress filter and `flight` has no `gap_segment`, `span_part` or `is_in_progress` column. Thirteen panel queries read `flight` directly (monday-events 1: card 156 since issue 324; military 2, pilot-onboarding 2, pilots-traffic 2, pilots-records 4: copies of cards 155, 129, 94 and 95; atc-positions 2: cards 94 and 95); the others read `flight_ext`, `movements` or `cohorts`, which follow `flight`. The panels about who is connected now (online now, pilots-now live views) read the live views `pilot_latest`, `pilot_online_now` and `online_now` and are unchanged. The earlier mechanism (a `NOT is_in_progress` filter on 11 panels and in `flight_ext`, owner decision on issue #38 of 09-10-2026) ran until 13-10-2026 08:14:12 UTC; it is recorded in CHANGELOG.md and ADR-025. Tests: `tests/test_phase3_switch.py` and `tests/integration/test_flight_views_switch.py`.

### Needs owner decision

- **Monday event attendance** (`monday_attendance` view; no panel charts it): it counts distinct pilot CIDs present at any time between 0700Z and 1200Z, a head count of people, not of flights, and, since phase 3, it reads finished flights through `flight` like every other flight count. Options: (a) leave it, so a pilot still connected during the event is counted as present (people are there); (b) exclude in-progress flights, so the current Monday under-counts until pilots disconnect, as v1 did for 8 hours. Recommendation: (a), because the panel answers who attended, and hiding people who are at the event right now would make the live Monday read low. Superseded by phase 3: the Monday is complete about 8 hours after the last pilot in the window disconnects.

*Decided for issue 89 phase 3 (owner, 12-10-2026; live since 13-10-2026 08:14:12 UTC):* Monday attendance follows the standard rule with no special case. The pilot side counts distinct pilot CIDs of finished `flight` rows that overlap 0700Z to 1200Z (`start_time < 1200Z` and `end_time >= 0700Z`), so a flight joined across a reconnect covers the gap and a pilot is counted once. Because only written flights exist, a Monday is complete about 8 hours after the last flight in the window ends (about 20:00Z or later), and the current Monday reads low until then. Controller side and columns unchanged. Tests: `test_every_flight_view_returns_the_same_rows_before_and_after_the_rename`, `test_monday_attendance_counts_a_pilot_only_once_the_flight_is_written`.
