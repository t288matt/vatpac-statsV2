# Chart definitions

Every in-scope v1 chart and what replaced it, for the Grafana dashboards in `grafana/dashboards/`. Dates are DD-MM-YYYY and all times UTC.

Status key: **KEPT** same question and definition (SQL rewritten against the v3 views); **CHANGED** same question, definition altered (see the difference column); **UNVERIFIED** the definition is the analytics agent's best reading and awaits the owner's Metabase export; **DROPPED** not rebuilt (reason given).

Panels read views and lookups only: `flight`, `controller_session_merged`, `online_now` and `data_freshness` from migration `20261007000004_views.sql`, most of the rest from migration `20261007000010_analytics_views.sql`, `controller_summaries` from migrations `20261008000030` and `20261008000031`, and `pilot_sample` from migration `20261008000080` (the `flight` view is now a thin view over the incrementally maintained `flight_summary` table, migration `20261007000020`). There is no backfill, so every chart starts empty at go-live.

Verification: on 07-10-2026 every panel query then existing (61) was run against the live local stack through Grafana's own API (`ops/check_panels.py`) with 0 errors (45 returned rows, 16 were empty because the data was only minutes old). The dashboards now hold 84 query panels (the 16 cards added after the snapshot, T15, were merged on 08-10-2026 and are not yet deployed or run on live data); the extra ones were checked statically (`python grafana/validate_dashboards.py` parses every query with sqlglot and resolves the views read, `grafana/check_columns.py` resolves columns) and by integration tests on synthetic rows, and the retention panel queries were run on the VM database through a temporary view (docs/TRACKER.md, T13). Running `ops/check_panels.py` on the VM after the next deploy is the remaining step. "Runs without error" is not the same as "answers the question correctly": the Test column says what to check once enough data exists.
