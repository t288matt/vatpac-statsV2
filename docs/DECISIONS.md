# Decisions (ADR log)

Each entry: decision, reason, consequence. Dates are DD-MM-YYYY.

## ADR-001 Rebuild instead of refactor (07-10-2026)
v1 (t288matt/vatpac-stats) is over-engineered: a 3.6k-line service class, sector tracking and ATC detection inside the ingest path, enrichment queues, archive copies, no keys or constraints. Rebuilt small, with its own schema. v1 is not modified or depended on.

## ADR-002 Frequency matching and sector matching are out of scope (07-10-2026)
Reason: they caused most of v1's cost and failures (slow queries, corruption, stalled summaries) and are not required. Consequence: the charts that need them are dropped (pilots on same frequency, % time/flights with ATC, sector charts, Milk Run Monday fastest/slowest, aircraft handled). Controller frequency is still stored so a stand-in can be added later without a schema change.

## ADR-003 Plain PostgreSQL 16, no TimescaleDB (07-10-2026)
Reason: volume is small (about 9 to 29 million raw rows at 90 days) and fewer moving parts is more supportable. Consequence: native daily partitions for `pilot_position`, partition create/drop done by the collector's maintenance task, no compression (about 2 to 3 GB), rollups as views or materialized views.

## ADR-004 Grafana as code instead of Metabase (07-10-2026)
Dashboards live in git as JSON and load on start, so the stack rebuilds from a clean clone. Metabase cannot load dashboards from files without a paid feature.

## ADR-005 Poll every 15 s aligned to the feed timestamp (07-10-2026)
The feed refreshes every 15 s (`general.update_timestamp`). v1 polled every ~92 s and saw one snapshot in six. v3 skips unchanged snapshots and records every attempt in `poll_log`.
*Superseded 09-10-2026 by ADR-024: the poll interval is now 30 s, held in POLL_INTERVAL_SECONDS.*

## ADR-006 Session identity (07-10-2026)
Flight and controller sessions are keyed `(cid, callsign, logon_time)`. Departure, arrival, route and aircraft are attributes, never keys (v1 keyed on them and produced duplicates).

## ADR-007 Filters (07-10-2026)
Kept: pilot boundary polygon, controller callsign whitelist (now fail-closed). Removed: callsign-pattern and frequency filters, which were inactive in v1 (the whitelist keeps ATIS and `_OBS` out). The flight-plan gate moves from ingest to a view so early positions are not lost.

## ADR-008 Retention (07-10-2026)
Raw positions 90 days; sessions and rollups permanent.

## ADR-009 Names and CIDs are stored and shown (07-10-2026)
As v1. When dashboards are exposed publicly (Cloudflare later) real names become visible; recommended: Cloudflare Access (login). Owner to check the VATSIM data-use policy before exposure.

## ADR-010 No REST data API (07-10-2026)
Only health/metrics endpoints. Dashboards read the database through a read-only role.

## ADR-011 No backfill (07-10-2026)
Charts start empty at go-live and show "data since <go-live date>".

## ADR-012 Watchdog authority (07-10-2026, amended)
The watchdog alerts and never changes data or config. Container restarts were originally in scope (through a restricted Docker socket proxy), but the owner chose to leave the socket proxy and any Cloudflare configuration out of this repo and to handle them externally later. So: no `docker-socket-proxy` and no `cloudflared` service in the compose file; the watchdog runs alert-only (HTTP health and database checks) unless `DOCKER_HOST_URL` is set to an endpoint provided outside the repo. Crashes are still restarted by Docker's `restart: unless-stopped`; a container that is running but unhealthy is not restarted automatically until that external piece exists.

## ADR-013 Hosting (07-10-2026)
Develop on Windows with Docker Desktop; deploy to an always-on Linux VM. Compose uses named volumes and no host paths except read-only `config/`.

## ADR-014 Collector size budget: 900, then 1300, now 1400 lines (07-10-2026)
The original budget (about 900 physical lines) was set before the required behaviour was specified in detail (retries and circuit breaker, SIGHUP reload with validation, near-miss tracking, partition maintenance, health endpoint, idempotent single-transaction ingest). The implementation is 1243 physical lines (comments and blanks included) with no module over 300, against v1's 12.8k lines for `app/`. The budget stays a hard gate (CI) so growth is a conscious decision. Raised again to 1400 after the review fixes (database timeouts, poison-record handling, reload alerting, flight-summary refresh loop) took the package to 1325 lines; each addition was a required behaviour, not feature creep.
*Superseded 08-10-2026 by ADR-022: the budget is now 1700 lines.*

## ADR-016 Flights are an incrementally maintained table, not a live view (07-10-2026)
*The pieces table described here is superseded by ADR-030; phase 5 (live since 13-10-2026, marker 7a71d30) dropped it and gave its name to the finished-flights table.*
The first design computed `flight` live with window functions over every position row. A reviewer measured 14 s at 8.9M rows (the 30 s dashboard limit is exceeded at the top of the expected size), and `monday_attendance` never finished. Now: `flight_summary` (keyed session, gap segment, span part) is recomputed every 5 minutes only for sessions seen in the last 12 hours (`refresh_flight_summary`, about 0.1 s) and finalised before a raw-position partition is dropped, so flights also survive the 90-day retention. `flight` is a thin view over it with the same columns. Measured on 10.5M synthetic rows: 12.5 s to 11 ms; `monday_attendance` 153 s to 61 ms; results identical (`flight_old EXCEPT flight` empty). Consequences: flight charts can lag live data by up to 5 minutes; changing `AIRBORNE_GAP_CAP_SECONDS` applies only to flights recomputed afterwards.

## ADR-017 Least-privilege database roles (07-10-2026)
The collector connects as `collector` (DML on its tables, EXECUTE on the maintenance functions, no DDL; the partition and refresh functions are SECURITY DEFINER), backups as `backup_ro` (`pg_read_all_data`), Grafana as `grafana_ro` (views and lookups, connection limit 10), the watchdog as `watchdog_ro`. The owner role is used by `migrate` and by restore only. Trade-off: the backup container still holds the owner password for the restore scripts; a dedicated restore role would be tighter.

## ADR-018 Airport movements stay the same as v1 (07-10-2026)
Owner decision: the movements charts keep v1's definition. Every flight-gate session counts as one departure at its departure airport and one arrival at its arrival airport, whether or not the aircraft ever became airborne. Evidence at the time: in v1's last full month (12-07 to 12-08-2026) 12% of home-region departures had zero airborne time and 6% were circuits, so the charts include parked connections. The `movements` view carries a SQL comment about this. A later change (an airborne-only panel or definition) needs a new decision and an ADR.
*Note 09-10-2026: the owner confirmed this again (issue 74, as v1 does; ADR-023 consequences). The `movements` view COMMENT (migration 20261007000024) said "SPEC decision pending"; migration 20261009000140 dropped that phrase and migration 20261009000150 now states the decided behaviour (issue 32). Flights still connected are no longer counted in movements, by ADR-025.*

## ADR-019 Names and CIDs are retained indefinitely (07-10-2026)
Owner decision, confirming ADR-009: no retention or anonymisation rule. Names and CIDs stay in the database and in backups for as long as the data is kept. ## ADR-021 Session identity uses whole-second logon_time (08-10-2026, owner decision)
Problem (T36, GitHub issue 15): the feed sometimes sends `logon_time` with fractional seconds and sometimes without. After a feed restart at about 04:08 UTC on 08-10-2026 every online connection lost its fraction, and because a session is identified by `(cid, callsign, logon_time)` with no tolerance, 31 pilot and 3 controller sessions were stored twice (flights about 7 to 8 percent too high).
Decision: `logon_time` is truncated (floor, not round) to whole seconds when the feed is parsed, for pilots and controllers, and the fraction is dropped on purpose. One callsign cannot log on twice in the same second, so nothing real is lost. Rounding was rejected because it would move a logon into the next second for some fractions and could still differ between two sightings that straddle .5. Truncation is stable: every form of the same second maps to the same value.
Rejected alternatives: matching with a tolerance (for example within 2 s) in the upsert, which needs a range lookup on every row of every poll, can chain, and leaves the table able to hold near-duplicates; storing the fraction as an attribute but keying on whole seconds (extra column nobody uses); merging twins only at report time in the views (every pilot view would need it, and the stored data would stay wrong).
Enforcement: migration 20261008000100 merges existing twins (survivor = lowest id, children re-pointed, flight_summary rebuilt), truncates every stored `logon_time` and adds CHECK constraints `pilot_session_logon_whole_second` and `controller_session_logon_whole_second`, so a regression fails loudly instead of duplicating sessions quietly. The fraction in already stored rows cannot be restored (the migration's down half only drops the constraints). A permanent check is `ops/audit/identity_flap.sql` (T16).

## ADR-022 Collector size budget raised from 1400 to 1700 lines (08-10-2026, ACCEPTED: owner approved on 08-10-2026)
The rolling raw-feed archive (issue 20, `archive.py`: compact record every 5 minutes, hourly full payload, anomaly payloads, retention and a hard size cap, run off the poll path in one worker thread) is a required behaviour of the permanent integrity checks (T16): it is the only way to replay a feed event such as the one behind issue 15, which could not be reproduced because no payload had been kept. It, plus its hooks in `main.py`, `feed.py` and `health.py` and the nine settings, takes the package from 1341 to 1575 lines, so 1400 cannot hold it (1652 lines on 09-10-2026 on the release branch, after the hardening work, with main.py trimmed to 280 lines by moving the resume-point reads and the poll statistics into `resume.py` and `pollstats.py`). The new limit is 1700, which leaves about 125 lines for the parallel hardening work (collector-hardening branch) and small fixes; the per-module limit of 300 is unchanged (`archive.py` is under 200). The gate stays hard: another rise needs a new decision. Rejected: a separate sidecar container for the archive (the audit's sketch), which would keep the collector small but adds an image, a second feed client hitting VATSIM and a second thing to monitor; and trimming features to fit.

## ADR-023 Reconnects of one flight are merged in the flight view, as v1 did (09-10-2026, owner decision; issue #35)
*Superseded by ADR-030 (phases 3 and 5 live, 13-10-2026): the join is made once by the writer, by v1's rule, and the view `flight_part` named below no longer exists (dropped by phase 5).*
Context: v1 grouped raw rows by callsign + CID + departure + arrival and split a flight only after a gap of more than 120 minutes (app/services/session_selector.py), so a pilot who disconnected and reconnected was still one flight. v3 identifies a session by (cid, callsign, logon_time), so every reconnect became a second flight. The v1 comparison (branch v1-comparison) found 49 of 234 v3 flights on 08-10-2026 had no airborne time; 32 of them were reconnect splits, and v3 counted 234 flights against 173 in v1.
Decision (owner, 09-10-2026, "merge them like v1 does"): the `flight` view merges parts of different sessions with the same cid, callsign, departure and arrival when the next part starts no more than 120 minutes after everything before it ended. Parts of one session are not joined, so the 8 hour span split is unchanged. A changed plan is a different flight, as in v1. `flight_part` keeps the per-session rows. Migration 20261009000110; no collector change.
Effect on the 08-10-2026 data (simulated from the live rows): 234 flights become 177 (v1: 173); flights with no airborne time fall from 49 to 16, which are stand-alone parked sessions.
Consequences: the merged row takes its first part's session_id, gap_segment, span_part and logon_time and its plan fields from the latest part. The view now does a window pass over all parts, so a panel query cannot push a time filter below it; at about 700 flights a day this is cheap, revisit if the table passes a few hundred thousand rows. Issue #74 (should parked sessions with no airborne time count as flights and movements) was decided by the owner on 09-10-2026: behave as v1 does. v1 counted every flight summary in its movement and count charts and filtered on enroute time only in the aircraft, online-by-hour and active-pilot charts; v3's rebuilt versions of those already filter on airborne time. No code change; 16 such flights remained in the 15 hour check window after the reconnect merge.
## ADR-024 Poll every 30 seconds, with everything cadence-dependent derived from one variable (09-10-2026, owner decision)
Context: the feed updates every 15 s; v1 polled about every 93 s; v3 polled every 15 s. Owner decision 09-10-2026: poll every 30 seconds, and the interval is not to be hard-coded anywhere but kept in the variable POLL_INTERVAL_SECONDS (default 30).
Decision: POLL_INTERVAL_SECONDS defaults to 30. Everything that depended on the old rhythm is derived from it: the airborne gap cap is 2.5 x the interval (75 s) and the archive gap threshold is 2 x the interval + 5 (65 s), both overridable by setting AIRBORNE_GAP_CAP_SECONDS or ARCHIVE_GAP_S (blank means derived); the collector publishes the interval to app_setting('poll_interval_seconds'); the "seen within the last two snapshots" windows in online_now and controller_session_merged.is_open are 2 x that setting (migration 20261009000120, no literal interval left); the soak report and the "Snapshots missed" panel read the cadence from the same setting (view poll_cadence).
Consequences: positions are stored half as often (smaller tables, coarser airborne minutes: each sample stands for 30 s and a missed poll leaves a 60 s gap, inside the 75 s cap); the collector reads every second feed update. For 24 hours after the deploy the "Snapshots missed" panel and any 24 h soak report mix both cadences and read wrong. Until the collector has started and published the setting, online_now shows nobody. Issue #42 (lower the interval to 10 s) is superseded.

## ADR-025 Flights still connected are excluded from the flight counts (09-10-2026, owner decision; issue #38)
*Superseded by ADR-030: the mechanism (`is_in_progress`) was removed in phase 3 because a flight is written only when finished.*
Context: v1 only summarised a flight 8 hours after it ended, so an unfinished flight was never counted there. In v3 about 5% of flights (18 of 382 at the audit) were still connected when a panel counted them, so flight counts, ranks and airborne-time sums moved as pilots were mid-flight. `flight.is_in_progress` (migration 20261009000130, ADR-023 merged flights) tells them apart.
Decision (owner): exclude in-progress flights from the COUNT panels (flights, ranks, airborne time, pilot and callsign counts per flight); keep them in the LIVE panels (pilots online now, departure board, online-now lists). Migration 20261009000140 filters `flight_ext` on `NOT is_in_progress`, so `movements` (both the departure and the arrival of the flight) and `cohorts` inherit it; the 11 panels that read `flight` directly carry `NOT is_in_progress` in their own SQL. Controller and session panels are not flights and are unchanged. The classification of every panel is in docs/CHART_DEFINITIONS.md ("In-progress flights").
Consequences: a flight appears in the counts once its pilot has been gone for two polls (60 s) rather than 8 hours, so it is counted about 8 hours earlier than in v1 but never while connected. A flight that reconnects within 120 minutes and is merged (ADR-023) drops out again while the new session is online and returns when it ends. If the collector stops, `online_now` is empty and every flight is counted. Panels that need an owner decision (monday attendance) are listed in the tracker row T46.

## ADR-026 Data retention rules for every data set (09-10-2026, owner decisions in chat; issue #21)
Context: the retention research of 09-10-2026 (read-only, live VM, about 1.8 days of data, so every projection is a rough estimate of plus or minus 40%) found that disk is not the constraint: the database is 49 MB on a 197 GB disk with 168 GB free; under the old rules it settles at about 1.3 to 1.8 GB, and keeping raw positions forever would take about 14 years (likely) to reach 80% full. The decisions are therefore about usefulness, safety and keeping dashboards correct. One date matters: raw positions have never been dropped on the live system and the first drop is due about 06-01-2027 (partition `pilot_position_20261007` passes 90 days); anything dropped is gone for good, because dumps cover 14 days and the raw-feed archive keeps compact snapshots for 30 days.
Decisions (owner), one rule per data set:
1. **Raw position samples (`pilot_position`): keep 180 days** (was 90). Setting `POSITION_RETENTION_DAYS=180`, to be live before 06-01-2027 (done 12-10-2026; the first drop is now about 05-04-2027). Cost about 0.9 GB. No dashboard looks back further than 7 days at raw positions; the reason for the longer window is a six-month period in which a rule mistake can be spotted and airborne time recalculated (it is frozen into `flight_summary` when the partition drops). **Superseded by ADR-030 and the amendments below:** flights are written once, about 8 hours after they end, long before any partition drops, and the drop gate refuses a day whose positions are not in a written flight.
2. **Pilot sessions, flight summaries, controller sessions and the two controller event tables: keep forever** (about 0.65 GB a year in total). Many panels are all-time (monthly totals, controller retention, cohorts, Monday attendance). No purge job. If one is ever wanted: positions must go before sessions (no cascade on `pilot_position`), controller events before controller sessions, and deleting a `pilot_session` deletes its `flight_summary` rows.
3. **Snapshot headline counts (`network_snapshot`): trim after 5 years** (about 87 MB a year). The `data_since` view is the minimum `observed_at` of this table and drives the "Data since" banner and the start of Monday attendance, so BEFORE any trim a stored go-live value must replace it (new numbered migration), so the date never moves.
4. **`poll_log`: keep the existing 400-day trim** (`POLL_LOG_RETENTION_DAYS=400`, about 350 MB at the cap).
5. **Raw-feed archive: no change** (compact files 30 days, full files 7 days, anomaly files 90 days, 1 GB hard cap; steady state about 0.65 GB, measured file sizes are about 50% larger than the runbook assumed; re-check at 14 and 30 days).
6. **Watchdog database-size warning lowered from 20 GB to 5 GB** (`WATCHDOG_DB_MAX_GB`), because the expected size is under 3 GB and the old limit could not catch a partition that failed to drop.
7. **Backups: keep 14 days of nightly dumps and add an off-VM copy of every nightly dump to a disk on the Proxmox host** through the existing `BACKUP_REMOTE` hook (rsync over ssh; runbook restore.md, "Off-box copies"). The destination is the same physical host, so it protects against a dead or corrupted VM disk but not against loss of the host; the Proxmox Backup Server job with its offsite sync (restore never tested, issue #26) remains the host-loss cover. Dumps contain real names and CIDs: the destination must be private and the key restricted. Not decided: a cap on the number of extra pre-deploy dumps (there is none today; 12 dumps accumulated in two days); recommended, to be confirmed.
8. **Small tables, Grafana data and Docker logs: no change.** Names and CIDs stay forever (ADR-019).
9. **Housekeeping, not retention:** about 70 unused anonymous Docker volumes (4.7 GB, left by earlier throwaway test databases), old images and the older rollback copies may be removed, but only from an exact list of names approved by the owner first. Never a blanket prune.
Consequences: nothing is deleted by these decisions today. Work to build, each needing an independent code review and then the owner's deploy go: the two settings (items 1 and 6), the `network_snapshot` trim with the stored go-live value (item 3; keep the logic in SQL because the collector size budget, ADR-022, is at 1696 of 1700 lines), the `BACKUP_REMOTE` configuration with the owner's one-time setup on the Proxmox host (item 7), and the clean-up list (item 9). Dashboards are unaffected: the longest look-back of any panel on a table with a rule is 7 days on raw positions (limit now 180 days), and every all-time panel reads a table kept forever or for 5 years.
**Amendment 12-10-2026 (issue 89 phase 4, issue 140; LIVE since 13-10-2026, marker 7a71d30 at 10:05:56 UTC).** Item 1 said the airborne time is frozen into `flight_summary` when the partition drops. Under option (c) of issue 89 the flight is written once into `flight_summary` (called `flight_record` when this was decided), 8 hours after the pilot was last seen, so the numbers are already safe long before a partition is due, and the drop gate no longer finalises anything. It asks instead whether the flights are safely written: a day is dropped only when every session with positions in it has `flown_upto` at or after the day's last position, every position of a session with a flight plan lies inside a written flight of that session, and every flight wholly inside the day has the right `sample_count`. Any doubt keeps the day (fail safe) and logs `DROP REFUSED`. The retention figures above are unchanged: the 180 days are still set by `POSITION_RETENTION_DAYS`, and with this gate live any retention is safe. The gate is live; at 180 days the first possible raw-position drop is about 05-04-2027, and the lock-hold time of one drop at live volume is to be measured before then (owner accepted on issue #140, 13-10-2026). See the amendment to ADR-026 item 2 under ADR-030 for deleting a session's flights.

## ADR-028 "Reactivated" needs an earlier session (10-10-2026, from the code review of issue 80; CONFIRMED by the owner on 10-10-2026)

## ADR-029 Publish all ten dashboards read-only with Grafana public dashboards (11-10-2026, owner decision)
Context: the owner wants anyone to see the dashboards, without a login and without any way to run their own queries. Grafana was upgraded the same day from 11.6.5 to 12.4.12 (the 11.6 line ended with 11.6.15 on 03-06-2026 and the `grafana-oss` image stops at 11.6.5, so the image became `grafana/grafana`, the OSS edition). The upgrade was tested first on a copy of the live `grafana_data` volume and deployed at about 19:40 UTC (commit 848526c).
Decision: use Grafana public dashboards, one public link per dashboard (token in the address) with a fixed time range, managed by `ops/grafana_public.py`, with fixed tokens and ten short addresses that redirect to the links (Traefik labels on the helper). Anonymous access stays OFF. Traffic path: Cloudflare (rate limit rule, Bot Fight Mode), Cloudflare Tunnel (named Home), Traefik on the owner's other machine, a small forwarder container `vatpac-proxy` (alpine/socat, standard Traefik labels) that passes on to Grafana at the VM's LAN address. Public name `vpac.mpengor.com` (changed from `vatpac.mpengor.com` so it does not show in searches for "vatpac"). Details, including the section "The Traefik machine (<TRAEFIK_HOST_IP>)" (outside this repository, not verifiable from it): [RUNBOOKS/public-access.md](RUNBOOKS/public-access.md).
Alternatives rejected:
- Anonymous Viewer: any visitor could send arbitrary SQL to the `grafana_ro` role through `/api/ds/query`. Rejected.
- `cloudflared` inside this compose file: the owner does not want it maintained there; the tunnel already exists on the Traefik machine.
- An nginx helper: one more web server to patch and configure; the owner rejected it for maintenance reasons. `socat` only forwards bytes.
- Traefik's file provider: switched off on that machine, and Traefik reads Docker labels only for containers on its own machine, hence the label-carrying helper.
- Grafana snapshots: a frozen copy, not live, and external snapshots are disabled in this stack.
Owner choices: all ten dashboards are public, including Collector health; each has a fixed time range with no picker; no Cloudflare WAF rule for the login and admin pages (the optional rule was offered and declined, so the Grafana login page stays reachable from the internet; the admin password is long and unique). The Departure board is fixed to YSSY because public dashboards do not fill text-box variables.
Consequences: a public page shows the SQL text of each panel, real names and CIDs (public VATSIM data, ADR-009, ADR-019), and runs queries on the production database for every visitor, bounded by the `grafana_ro` limits and the Cloudflare rate limit. The links live in the `grafana_data` volume; their tokens are fixed, so recreating them gives the same addresses. Cloudflare and the Traefik machine are outside this repository. Rollback of the upgrade: `~/grafana_data_pre_12.tgz` and `~/vatpac-statsV2.rollback-11-10-grafana` on the VM. Dependabot ignores major versions of `grafana/grafana`.

## ADR-030 Flights are written once, when finished, into `flight_summary` (called `flight_record` until phase 5); quiet per flight (issue #89; owner decisions 12-10-2026; phases 1, 1b, 3, 4 and 5 all LIVE: phases 1, 1b and 3 since 13-10-2026 08:14:12 UTC at the latest, phases 4 and 5 since 13-10-2026 10:05:56 UTC, marker 7a71d30)

Context: the `flight` view glued small per-session pieces (`flight_summary`) into flights every time a chart opened, so charts slow down as history grows (issue #89). The owner chose option (c) on 12-10-2026.

Decision (owner):
- **Write once.** A flight is one row in the new table (`flight_record` until phase 5, now `flight_summary`), written by `write_finished_flights()` straight from the raw positions and never changed. Charts read these rows since phase 3 went live (13-10-2026 08:14:12 UTC, marker 38e3958). Phase 5 dropped the pieces table and renamed `flight_record` to `flight_summary`. Phases: 1 writer and backfill (deployed 12-10-2026, marker c70e72f at 17:58:21 UTC), 1b quiet per flight (deployed 13-10-2026, marker 3d4b5b6 at 08:01:09 UTC), 3 switch the `flight` view and panels (deployed 13-10-2026, marker 38e3958 at 08:14:12 UTC), 4 replace the raw-data drop gate with a reconciliation against written flights (deployed 13-10-2026, marker 7a71d30 at 10:05:56 UTC), 5 delete the pieces and rename (deployed in the same deploy, marker 7a71d30; the table is now `flight_summary`).
- **Quiet per flight, not per pilot (owner decision 12-10-2026, replaces design 1.3).** A flight is written when the flight itself has had no position for 8 hours (`app_setting.flight_quiet_hours`), measured against the newest stored snapshot (never the wall clock; capped at now plus 5 minutes). The first live run showed that waiting for the whole pilot to be quiet held back every older flight of the 141 pilots who were online again. Migration 20261012000200; deployed 13-10-2026 (marker 3d4b5b6, 08:01:09 UTC).
- **The flight rule is v1's rule.** Same CID, callsign, departure, arrival; a new connection joins when it logged on within 120 minutes of the latest earlier last position; no 8-hour parts and no cut inside a connection (amends ADR-023, which kept the 8-hour span split and joined from the first position).
- **Airborne time keeps v3's measured-gap rule** (each gap capped at `airborne_gap_cap_seconds`, a pair more than 120 minutes apart counts zero), not v1's sample count times the poll interval.
- **Retention lever.** `POSITION_RETENTION_DAYS=180` (issue #142, phase 0) moves the first raw-data deletion from about 06-01-2027 to about 05-04-2027 (by the partition arithmetic: the first partition, 06-10-2026, ends 07-10-2026 and is due 180 days later), so the new drop gate can be built and rehearsed without a deadline (amends ADR-026 only in the date).
Supersedes: ADR-016's piece table and ADR-025's in-progress mechanism. Phase 3 (live since 13-10-2026 08:14:12 UTC) removed the in-progress filter from the charts, and phase 5 (live since 13-10-2026 10:05:56 UTC) removed the piece table and the comparison-only view `flight_legacy` (see below).

**Phase 5 (issue #141, migration 20261013000300; LIVE since 13-10-2026, marker 7a71d30, applied in 67 ms).** The old pieces table, the views `flight_part` and `flight_legacy`, and the functions `refresh_flight_summary` and `refresh_flight_summary_sessions` were dropped (without CASCADE, in dependency order); `flight_record` was renamed `flight_summary` with its primary key, CHECK constraint and four indexes; the writer, the reconciliation helper and the drop function were re-created with only the table name changed. The collector's 5-minute job calls `write_finished_flights(50)` itself (EXECUTE granted to `collector` in the migration and in `db/roles.sql`); a statement timeout is logged and the next run continues. The two watchdog checks about the pieces were removed (23 checks became 21). Forward-only: the way back is the pre-deploy dump (taken 13-10-2026 10:00 UTC, restore-tested). Dumps made before the deploy hold the finished flights as `flight_record` and the pieces as `flight_summary`; the restore check reads `flight_record` first. History in older ADRs and migrations keeps the old meaning of the name `flight_summary`. Read on the live database after the deploy: `flight_summary` 1797 rows; the old objects do not exist; 22 views, 8 functions, 3 foreign keys.

**Amendment to ADR-026 item 2 (phase 5).** The pieces table had a foreign key to `pilot_session` with ON DELETE CASCADE; the flight table has none. A manual delete of a session must therefore also delete its flights: `DELETE FROM flight_summary f USING pilot_session s WHERE s.id = ANY (f.session_ids) AND f.cid = s.cid AND s.id = <id>` (served by the `cid` index). No purge job exists, so this is a rare manual step. The comparison with the old table's rule: the flight, not the session, is the unit that survives the raw positions.
Consequences: a finished flight appears in the charts about 8 hours after it ends (plus up to 5 minutes); a flight that is still being continued by a reconnect appears 8 hours after the last connection of the joined flight; plan fields are frozen when the flight is written. Verification: the exit test of 13-10-2026 (CHANGELOG.md "Exit test of phase 1 (#138)": 974 of 998 v1 raw-position flights match one to one, 0 split).

## ADR-031 Deploy by git checkout plus commit-tagged registry images (hybrid) (14-10-2026, issue 173; the hybrid is an owner decision of 14-10-2026; phases P0 to P3 DEPLOYED and verified on 14-10-2026 on the owner's go, P4 documents in a draft pull request; the owner confirmed on 14-10-2026 that the hybrid is the chosen method and that the packages show Private)
Context: a deploy was `git archive | ssh ... tar -x` plus building four images on the VM. `tar -x` never deletes, so the VM holds stale files (15 on 14-10-2026, including old comparison scripts; a stale migration file would be applied). Building on the VM costs time and CPU on the live host. An Opus plan review of 14-10-2026 advised against the first plan (option A: everything baked into registry images, a second compose file).
Decision (owner, 14-10-2026): the smaller hybrid. (1) The VM becomes a read-only git checkout (deploy key). (2) The four images this project builds (collector, watchdog, backup, migrate) are built by GitHub Actions and pushed to private GHCR; `db/` is baked into migrate as well as mounted. (3) Dashboards, provisioning, `config/` and `ops/postgres/postgresql.conf` stay bind mounts from the tree. (4) One compose file, two modes, chosen by `VATPAC_IMAGE_PREFIX` and `VATPAC_IMAGE_TAG` (both unset: local build as before; both set: registry; one alone fails `ops/check_env.sh`).
Followed in the 14-10-2026 run on the owner's go; the owner has not yet separately confirmed them as the standing rule (to be confirmed): tags by commit, `sha-<first 7 characters>`, never `latest`, and no semver (deploy.sh preflight and `--mark` already work on commits, so marker and images name the same thing; a tag also makes a rollback exact). Publishing by a manual `workflow_dispatch` for a commit that is on main with a green CI run, which builds and pushes but does not repeat CI (paying for CI twice was the review's finding). A classic personal access token with only `read:packages` and a 90 day expiry on the VM, because GHCR accepts classic tokens only (GitHub Docs, read 14-10-2026); the owner keeps a calendar reminder.
Alternatives rejected: full option A, because baked dashboards would be hidden by the `grafana_data` volume mounted over `/var/lib/grafana`, the VM still needs the tree for `deploy.sh --verify`, `ops/smoke.sh`, `ops/check_panels.py` and `ops/grafana_public.py`, and a second compose file would drift from the one the tooling and tests pin; semver tags (nothing else here uses them, and the marker is a commit); `latest` (no exact rollback); re-running CI on a tag (cost).
Status 14-10-2026: the VM is a read-only git checkout; commit 67c1ca0 was published and deployed (marker 22:29:46 UTC, `--verify` 10 PASS); the token expires about 12-01-2027 (reminder 05-01-2027). Not yet run: a second registry deploy, a rollback to a previous `sha-` tag (the first rollback can only use the local `:local` images, because no earlier registry tag exists), a token renewal. The packages are private (confirmed by the owner on the GitHub Packages page, 14-10-2026). On the VM `up -d --build` must not be used in registry mode: it rebuilds locally and retags the registry name.
Amendment 15-10-2026 (owner decision): a deploy needs no `.env` edit. The release workflow still publishes every image as `sha-<7>` (history and rollback) and, once all four are pushed, moves the plain tag `latest` to them. The compose default tag is now `latest` (was `local`; local builds are named `:latest` too), so the VM's `.env` needs one line, `VATPAC_IMAGE_PREFIX=ghcr.io/t288matt/`, and `VATPAC_IMAGE_TAG` is an optional override used only to pin a previous build (the both-or-neither rule is gone; a `sha-` pin is warned about). One-time VM change: delete the `VATPAC_IMAGE_TAG=sha-...` line. The routine is `make deploy`: `git pull --ff-only`, `docker compose pull`, a check that the pulled images' revision label equals the checkout commit (stop if not), then `docker compose up -d --no-build`. Why: fewer manual edits (a typo made a duplicate pair of lines on 14-10-2026), and the release click stays the approval gate. Trade-off: `.env` no longer records the exact commit; the image revision label and the release marker do. This reverses the 'never `latest`' wording below. The text below is the 14-10-2026 method as decided.
Consequences: a deploy is `git checkout`, `docker compose pull`, `docker compose up -d --no-build`; stale files cannot survive. Images cannot undo a migration, so the dump-first rule stays for every deploy. The token reads every package the account can reach and expires: on expiry deploys fail (`unauthorized`) while the running stack is unaffected, so a reminder is needed; the credential sits in `~/.docker/config.json` on the VM. The backup image's `EXTRA_APT_PACKAGES` build argument no longer applies in registry mode (an off-box copy hook that needs `rsync`, `ssh` or `rclone` needs local-build mode until the tools are in the image). GHCR storage, quota and package privacy were not checked (the CLI token gets 403 on packages). The old `git archive` method stays documented as a fallback. Not decided here and parked: floating major tags for the third-party images (issue 176), the Grafana boot race (issue 164). Runbook: [RUNBOOKS/deploy-to-vm.md](RUNBOOKS/deploy-to-vm.md) sections 2d to 2f.

Amendment 04-11-2026 (owner decision, issue 268): the release workflow also runs by itself when `ci` finishes successfully for a push to main, and publishes that commit only if it is still main's tip (a stale run publishes nothing, so `latest` never moves backwards). The manual run stays for rollbacks and for a docs-only tip. Nothing deploys automatically: the owner still runs `make deploy` by hand, and `ops/check_pulled_images.sh` still refuses to start anything when the pulled images do not match the checkout. Cost: one four-image build per green merge to main, including changes that touch no baked file (workflow-only commits); skipping those is a possible later change.

## ADR-032 Third-party images take small updates automatically: floating major tags (15-10-2026, issue 176, owner decision)
Context: Postgres, Grafana and dbmate were pinned to exact versions (`postgres:16.15-bookworm`, `grafana/grafana:12.4.12`, `amacneil/dbmate:2.36.0`), and each small update needed a Dependabot pull request, a test and a merge. The owner first asked for `latest`; `latest` was refused because `postgres:latest` is a new major version that cannot open the existing version 16 data directory, and `grafana/grafana:latest` can jump a major version.
Decision: the three images use the major version only: `postgres:16-bookworm` (database, backup image and CI service `postgres:16`; the Debian variant stays), `grafana/grafana:12` and `amacneil/dbmate:2`. Our own images and the Python base images are unchanged. A new major version stays a deliberate edit of the tag, after a test and, for Postgres, a dump and restore plan. Dependabot keeps its major-version ignores for these images, so it cannot propose a jump.
**Amended 18-10-2026:** `grafana/grafana:12` is not a tag Docker Hub actually publishes for that image (confirmed against its registry API: only `MAJOR.MINOR` and more specific, e.g. `12.4`, `12.4.13`, never a bare major) — `docker compose pull` on the VM failed with `manifest unknown` on first use. Postgres and dbmate do publish a bare-major tag and are unaffected. Grafana now floats on `grafana/grafana:12.4` (minor instead of major); nothing else in this decision changes. No CI job pulls the real image (integration tests only use Postgres for the `grafana_ro` role; `validate_dashboards.py` is a static JSON check), so this class of error is not caught before a real deploy attempt.
Trade-off in plain words: updates now arrive with each `docker compose pull` (and `docker compose build --pull` for the backup and migrate images) and nobody reviews them first. A deploy can therefore change Postgres or Grafana without a code change; `docker compose up -d --no-build` alone does not fetch anything, so nothing changes unless a pull is run. Postgres minor updates are safe in place. Grafana minor updates can change its data volume, and going back to an older Grafana version cannot undo that, so the habit stays: copy the `grafana_data` volume before a deploy that pulls (command in RUNBOOKS/public-access.md, "Roll back") and keep the copy until Grafana and the ten dashboards are confirmed healthy. Rollback of an image is by its digest (`docker image ls --digests`), and the dump-first rule stays because an image cannot undo a database change.
Consequences: after a deploy that pulled, run `bash ops/deploy.sh --verify` and check Grafana health (RUNBOOKS/deploy-to-vm.md). CI and the VM can run different patch versions on the same day. The backup image is built when a release is published and the database image is pulled at deploy time, so their Postgres versions may differ by a patch release inside major 16, which `pg_dump` accepts. `ops/deploy.sh --mark` appends `thirdparty=` (the image digests of db, grafana and the dbmate base, or `unknown` when they cannot be read; never anything from `.env`) to the `.deploy/release.log` entry, which gives the digest to roll back to; the release file is unchanged. Not done: printing the versions in `--preflight` (issue 176, work item 3, smallest version only). The deploy runbook now has the pre-deploy Grafana volume copy as a step. `tests/test_compose_image_vars.py` fails if one of these images is `latest` or an exact patch, or if the database and backup tags differ. The release log line records the digests of the db and Grafana images; the Dbmate base image is usually not stored on the VM (only the pulled migrate image is), so that digest usually reads `unknown`. The db and Grafana digests are the ones that matter for rollback.

## ADR-033 Collector and watchdog move to Python 3.14, and CI tests on 3.14 (15-10-2026, issue 174, owner decision)
Context: the images were `python:3.12-slim` and CI tested on 3.12, while Dependabot proposed 3.14 for both images (pull requests 170 and 171). The 3.14 bump failed CI only because numpy was pinned to 1.26.4; numpy is now 2.3.5 (the first line with 3.14 wheels), live on the VM.
Decision (owner, 15-10-2026): the collector and watchdog images use `python:3.14-slim`, and every CI job uses Python 3.14, so the tested Python is the shipped Python.
Reason: one interpreter for testing and shipping is simpler long term than holding 3.12 and having Dependabot raise the bump again; it also removes a gap where something passes on one Python and breaks on the other.
Trade-off: a newer interpreter, so every pinned package must publish a wheel for CPython 3.14 on linux x86_64. Checked 15-10-2026: all pins in `collector/requirements.txt` and `ops/watchdog/requirements.txt` (and their dependencies) have cp314 or pure-Python wheels, so no pin changed. The unit suite passes on 3.14.8, also with DeprecationWarning treated as an error.
Consequences: a future package that lacks a 3.14 wheel blocks its own bump until it ships one. Local helper scripts still accept Python 3.11 or newer. Dependabot pull requests 170 and 171 are superseded by this change.

## ADR-035 Load v1 history from the two v1 summary tables into `flight_summary` and `controller_session` (05-11-2026, issue 279, PROPOSED: owner decisions of 05-11-2026 recorded, design review and the owner's go still to come)

T22 said the decision could be reopened. v1 still holds summaries from 24-08-2025. Read-only profile of v1 on 05-11-2026, for the range chosen below: 73,532 rows in `flight_summaries` (24-08-2025 to 06-03-2026) and 11,270 in `controller_summaries` (24-08-2025 to 15-03-2026); v1 has no summaries for 04-2026 to 06-2026 and almost none for 09-2026.

3. Flights: `session_id` and `session_ids` are the negative of the v1 id, so imported rows cannot meet live rows. `end_time` is v1 `completion_time`, which is the end of the session window when the summary was written, not the last position; `start_time` is `completion_time` minus `time_online_minutes` (v1 sets that as last minus first position of the leg; start minus logon has a median of 2.2 minutes and never goes before logon). `airborne_minutes` is `least(total_enroute_time_minutes, time_online_minutes)`: `total_enroute_time_minutes` is v1's airborne time (positions at 60 kt or more; docs/V1_COMPARISON.md 6.6 found v3 airborne about 5% above it), capped because 2,192 of 73,532 rows exceed time online (v1 matched positions by callsign and time window only). 0 imports as 0, not NULL. `max_gs_kt` and `max_alt_ft` are NULL and `sample_count` is 0 (the carried-over convention). `aircraft_icao` comes from `aircraft_type` (`aircraft_short` is empty in 97%); `home_icao` is parsed from `name` by the collector's rule; `remarks` is NULL.

ON CONFLICT DO NOTHING` (the controller key is `(cid, callsign, logon_time)`; flights are keyed by the negative id); rehearsed on a throwaway database with synthetic rows, never on a copy of production; Behaviour preserved section; a fresh dump before the load; the owner's explicit go for the load (one go).
