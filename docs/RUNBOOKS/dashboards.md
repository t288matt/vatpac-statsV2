# Runbook: add or change a dashboard

Last reviewed: 15-11-2026. Dashboards are code: JSON files in git, loaded by Grafana from a read-only mount. Edits made in the Grafana web interface are not saved (`allowUiUpdates: false`, viewers cannot edit) and are lost on restart; every change goes through the files.

## Where things are

- `grafana/dashboards/<folder>/<name>.json`: one file per dashboard. The directory name becomes the Grafana folder (`pilots`, `atc`, `events`, `demographics`, `military`, `monitoring`).
- `grafana/provisioning/dashboards/dashboards.yml`: loads every file under that directory and rescans every 30 seconds. `grafana/provisioning/datasources/postgres.yml`: the single data source `vatpac` (uid `vatpac`), connecting as the read-only role `grafana_ro`.
- `grafana/validate_dashboards.py`: the static check below. Every panel query is also run against a real database by `tests/integration/test_audit_t30.py::test_every_panel_query_runs_as_grafana_ro`.
- `docs/CHART_DEFINITIONS.md`: one row per chart saying what it shows, where it comes from and how to test it.

## The rules a dashboard must follow

`python grafana/validate_dashboards.py` enforces these (it fails CI):

- Valid JSON with a unique dashboard `uid` (convention `vatpac-<name>`), a title and `"timezone": "utc"`.
- A top text panel (id 1) with a navigation strip (generated by `ops/dashboard_nav.py`; see [public-access.md](public-access.md), "Add or rename a short address"; the links are anchors with `target="_top"`) and, since 08-11-2026 (issue #307), the sentence "All times are UTC. Figures cover VATPAC airspace." (the earlier data-history banner was removed; `grafana/validate_dashboards.py` requires "All times are UTC" in a text panel). The hidden `go_live` constant variable stays on every dashboard although only the Collector health text panel uses it now (the value of `data_since.go_live`, 07-10-2026 21:38 UTC; it is a constant because public dashboards cannot run variable queries; if the data start date ever changes, update it in all 17 dashboards). There is no backfill, so every chart starts empty at go-live (the v1 history import of ADR-035 was loaded on 05-11-2026; see [import-v1-history.md](import-v1-history.md). The `go_live` value was not changed by it).
- Unique panel ids; every non-text panel uses the data source with uid `vatpac` and has a non-empty `rawSql`; give every panel a description (a warning otherwise). Say which v1 card it reproduces.
- Queries read only allow-listed relations: the views created in `db/migrations/` and the six lookup tables (`controller_rating`, `facility`, `pilot_rating`, `airline`, `aircraft_type`, `region_map`). Base tables such as `pilot_session` or `poll_log` are refused, and `grafana_ro` has no access to them anyway. The list of views is in [../DATA_DICTIONARY.md](../DATA_DICTIONARY.md).
- No hard-coded dates, no `DISTINCT ON`, and every query must parse as PostgreSQL (needs `pip install sqlglot`; without it the SQL is not parsed and the script says so).
- Dashboards listed in `RESTYLED` in `grafana/look_rules.py` also follow the look conventions below; the validator fails on a colour outside the palette (a named colour, a short hex or one with an alpha part counts as outside), a donut that is not a donut with a legend table and the classic palette (or any other panel using the classic palette), a table whose `cellHeight` is not `md`, an in-cell bar that is not mode `basic` with the value as text, a time series without a legend table or the opacity gradient, a bar chart that hides its values (other than the hours-of-day charts), a change arrow with no `timeFrom` window to compare against, or a `trend` panel. The rules read type, options and field settings only, never a query. `tests/test_dashboards_look.py` runs the same rules.
- Use UTC explicitly, and Grafana's time macros (`$__timeFrom()`, `$__timeTo()`, `$__timeFilter(col)`) or `now()` so the chart follows the time range.

## Look conventions (issue 280, the former "Pilots: online now" look)

One look on every page, so a restyle changes `type`, `options` and `fieldConfig` and never a query. The pages restyled so far are listed in `RESTYLED` in `grafana/look_rules.py` (today: Traffic, Routes, Aircraft, Pilots records, the five ATC pages, Monday events, Monthly, Collector health, Pilot origins, Military, Pilot onboarding); that is every page.

- **Colours:** fixed, never by theme. Blue `#3AA0DD` (first series and every single-colour chart), amber `#E69F00` (second series), green `#1FAF8A`, pink `#CC79A7`, grey `#8A97B2`, and red `#D55E00` only for "bad" (status-card limits, the error series on Collector health). The one exception is a donut, which has one colour per slice and an unknown number of slices, so it uses Grafana's classic palette (`color.mode` `palette-classic`).
- **Tables:** `cellHeight` `md`, no footer. The main count column of a ranked table is an in-cell bar (`custom.cellOptions` type `gauge`, mode `basic`, value as text, minimum 0, blue). Grafana scales the bar against the largest value of any number column in the table, so a table that mixes scales (minutes beside counts, groundspeed beside altitude, percentages beside counts) gets no bar, and the bar goes on the largest column. Status columns are pills with the fixed colours (see the departure board on Live now). Column names come from the query and are not renamed here.
- **Ranked bar charts:** horizontal, values shown, one fixed colour per series, legend as a plain list at the bottom (hidden on "Active pilots and controllers"; the checker does not look at the legend of a bar chart). "Active pilots and controllers" on Pilots records keeps the chart's own orientation. Hours-of-day charts stay vertical without values (24 bars) and use the Live now settings; the `trend` panel type is not used.
- **Time series:** smooth line (or bars for per-week counts), opacity gradient, no points, legend as a table with last, max, min and mean. A chart with several series gives each series one fixed colour by name; the six rating groups use blue, amber, green, pink, grey and a dashed blue line for I1+, and the eight position types of the stacked weekly hours use the five colours plus three paler repeats (FSS, DEL, FMP). Hours-by-weekday tables on Ranks are heat tables: blue gradient background (`continuous-blues`) with the hour column left plain.
- **Donuts:** donut with a legend table (value and percent) on the right, in the order the query returns, largest first. A donut or a ranked bar is added or removed only on the owner's decision for that panel.
- **Stat cards:** a plain card (no sparkline, no arrow, fixed colour) unless the query returns a series to compare; a status card (Collector health) takes its colour from its limits: green, amber from the first limit, red from the second; the arrow shows only where it compares a real earlier value (the first two cards on Live now, "vs 1 hour ago").
- **Text:** panel 1 (navigation strip and sentence) is generated and does not change; no generated headline sentences.
- **Do not change a query in a look change.** `tests/test_dashboards_sql_unchanged.py` compares a hash of every panel's `rawSql`, `format` and `timeFrom` with `tests/fixtures/dashboard_sql_baseline.json`. A query change needs the owner's explicit yes for that panel; the same pull request then rewrites the baseline with `python tests/test_dashboards_sql_unchanged.py --write` and says so.
- **Copies:** a panel that is a copy of a panel on another dashboard is restyled with its source. While a copy's page is not yet restyled, the `RESTYLED` set in `tests/integration/test_atc_live_events.py` or `tests/integration/test_routes_aircraft.py` (whichever tests that copy) names the restyled panel, and a test in each file fails when an entry no longer differs from its copy, so a stale entry is removed; the tests still compare query, format and window for every copy. Remove a name from `RESTYLED` when the copy's page is restyled. The two "When are people online" copies on ATC positions stay in that set on purpose: they plot Pilots and ATC with a legend and two colours, while Live now plots Pilots only, so their options differ; query, format and window are still compared.
- What Grafana cannot do on a public dashboard (do not attempt): sidebar or menu, Share button, visitor theme switch, per-card toggles or refresh, donut centre total, card shadow or radius, hiding the title bar, monospace figures, sparklines that do not overlap the number.

## Collector health: the two daily panels (issue 27)

The two lower panels of `monitoring/collector-health.json`, "Database size vs VM disk" and "Database speed", read the view `health_sample`, which has one row per UTC day (see [DATA_DICTIONARY.md](../DATA_DICTIONARY.md), `system_sample`). The collector's daily maintenance job writes the row; the graphs start on the first day it ran and each shows the last 400 days (panel setting `timeFrom`). "Database size vs VM disk" draws the database in MB on the left axis (blue) and the free space on the disk that holds the database in GB on the right axis (amber), so the headroom before the disk fills is visible. Free is total minus used, which is higher than the figure `df` calls available by the reserved slice the system keeps, about 5% of the disk's total size. The two scales differ because the database is under 1 GB while the disk is far larger. "Database speed" draws the time to count the flights of the last 30 days, in milliseconds: flat is healthy, rising means more data or a slower server. One day without a point means that day's reading failed (the collector log says "system sample skipped"); the next day's reading is unaffected.

## Add or change a panel

1. **Write the query against the views** in `psql` first. On the VM: `docker compose exec db psql -U vatpac -d vatpac`. The query must also work as `grafana_ro`, which sees views only. Mind cost: Grafana's statement timeout is 30 seconds, and the panels run every 30 to 60 seconds. Avoid reading `pilot_position` (it is not exposed); use `flight`, `flight_ext` and the other views.
2. **If a view is missing**, add a new numbered migration in `db/migrations/` (file name `<timestamp>_description.sql` in the same 14-digit style, later than the latest, with `-- migrate:up` and a `-- migrate:down` stub that says it is forward-only). Never edit an applied migration. Every view in `public` is granted to `grafana_ro` the next time the `migrate` job runs `db/roles.sql`, so no grant line is needed. Document the view in [../DATA_DICTIONARY.md](../DATA_DICTIONARY.md).
3. **Edit the dashboard JSON**: copy a similar panel in the same file, give it the next unused `id` and a free `gridPos`, then set `title`, `description`, `fieldConfig` and `targets[0].rawSql` (`"format": "table"` for tables and stats, `"time_series"` for time series, with a column named `time`). A panel can set its own window with `timeFrom` (pilots-now: `1h` on the three stat cards, `24h` and `7d` on its two line charts); without it the panel follows the dashboard's time range. Keep the JSON valid (the validator reports the file and panel on error).
4. **Update the documentation in the same commit:** the row in [../CHART_DEFINITIONS.md](../CHART_DEFINITIONS.md) (v1 card, definition, source view, panel file and title, difference from v1, status, test) and the summary counts if a card moved between KEPT, CHANGED and DROPPED; the "why these charts were dropped" notes in the same file if a chart is dropped.
5. **Test it** (next section), commit, and deploy ([deploy-to-vm.md](deploy-to-vm.md)). A JSON-only change needs no rebuild or restart; Grafana picks it up within 30 seconds.

## Test a dashboard change

Without a database (anywhere, fast):

```sh
python grafana/validate_dashboards.py     # expect RESULT: OK (0 errors); it prints a WARNING for each panel with no time range, now() or live view (a new warning means a new panel to check)
```

Against synthetic data, on a throwaway database named `*_test` (see [run-tests.md](run-tests.md)): the integration tests load the dashboard JSON, take the panel's `rawSql`, replace `$__timeFrom()` and `$__timeTo()`, insert synthetic flights or sessions and assert on the result. To cover a new or changed panel, add a test in `tests/integration/` beside the existing ones (for example `tests/integration/test_card_90.py`, which reuses `run_panel` and `add_flight` from `tests/integration/test_pilots_t14.py`). The marker is `@pytest.mark.integration`.

Against real data, read-only, on the VM: take the panel's `rawSql`, replace `$__timeFrom()` with `(now() - interval '200 days')` and `$__timeTo()` with `(now())` (keep the brackets), wrap it as `SELECT count(*) FROM (...) x`, and pipe it to `psql` in the db container. Check the result against a manual count.

Through Grafana, after a deploy: `python3 ops/check_panels.py` (from the stack folder, on the VM) runs every panel query via Grafana's API and reports OK, EMPTY (no rows yet, fine while data is young) or ERROR. Then look at the dashboard in a browser: a query that runs is not the same as a query that answers the question correctly.

Names and CIDs are shown and are public VATSIM data. Public, read-only sharing is done with Grafana public dashboards and is described in [public-access.md](public-access.md) (ADR-029); anonymous access stays off. Public dashboards do not fill text-box variables, so a dashboard that is shared needs a fixed value in place of a text box (the Departure board is fixed to YSSY). Each shared dashboard also needs a short name in `SHORT_NAMES` in `ops/grafana_public.py` (a test requires it); see the short-address steps in [public-access.md](public-access.md).
